## Проблема 1 — Laser filter: только передние 180°

**Файл:** `config/laser_filters/laser_filter.yaml`

**Суть:**
Лидар видит только переднюю полусферу. В узком коридоре:
- При повороте сцена меняется кардинально от скана к скану
- Стены слева/справа создают симметричную геометрию — matcher может спутать 0° и 180°
- Задняя стена (которая могла бы "якорить" позицию) полностью срезана

**Почему фильтр был введён:**
Срезаем корпус робота, который попадает в задние 180°.

**Пути решения:**

### Вариант A — Оставить полный 360°, вырезать только корпус точечно (рекомендуется)
Вместо углового среза — вырезать только те сектора, в которых физически стоит корпус:
```yaml
# Пример: вырезать только углы, где корпус реально мешает
scan_filter_chain:
  - name: range
    type: laser_filters/LaserScanRangeFilter
    params:
      lower_threshold: 0.20
      upper_threshold: 6.0
  - name: shadows
    type: laser_filters/ScanShadowsFilter
    # ... точечные угловые маски вместо -90..+90
```
Требует замера реальных углов, в которых корпус попадает в скан.

### Вариант B — Расширить фильтр до ±150° (быстрый тест)
Даст SLAM данные о боковых стенах без изменения основной логики:
```yaml
angle_min: -2.618  # -150°
angle_max:  2.618  # +150°
```

### Диагностика
```bash
# Посмотреть реальный скан лидара без фильтра
ros2 topic echo /scan_raw --once
# Или в RViz добавить /scan_raw рядом с /scan — видно что срезается
```

## Проблема 2 — Wheel slip при вращении на месте

**Файл:** `firmware/esp32_chassis/`, `config/robot_localization/ekf.yaml`

**Суть:**
При вращении на месте (левое колесо назад, правое вперёд) оба колеса несут полную нагрузку
в противоположных направлениях. На паркете/плитке внутреннее или оба колеса могут скользить.
Энкодеры фиксируют вращение колеса, а не перемещение пятна контакта.

**Диагностика (обязательно перед правками):**
```bash
# 1. Поставить маркер на полу, выровнять робота по нему
# 2. Командой повернуть ровно на 360°:
ros2 topic pub /cmd_vel geometry_msgs/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.5}}" --times 1
# Через ~12.6 сек остановить.
# 3. Сравнить реальный угол с /odom theta (должен быть ~0 после 360°)
ros2 topic echo /odom --once | grep -A3 orientation
```

**Пути решения:**

### Вариант A — Снизить скорость вращения в Nav2 (быстро)
Медленнее = меньше slip. В `nav2_navigation_params.yaml`:
```yaml
# RotateInPlace behavior или controller
max_vel_theta: 0.4   # было выше — снизить
min_vel_theta: 0.1
```

### Вариант B — Запретить вращение на месте, использовать arc-повороты
В DWB/RPP контроллере включить минимальную линейную скорость при повороте:
```yaml
# В nav2_navigation_params.yaml для controller_server
min_vel_x: 0.05  # небольшой forward drift при повороте = меньше slip
```

### Вариант C — IMU как основной источник yaw (долгосрочно)
Если IMU гироскоп достаточно точен (BMX055 — drift ~0.005 rad/s):
- В `ekf.yaml` повысить доверие к `imu0` vyaw (снизить covariance IMU)
- Откалибровать gyro bias (сейчас не откалиброван)
- Тогда EKF сможет корректировать yaw от энкодеров данными гироскопа

## Проблема 3 — `link_match_minimum_response_fine: 0.1` (слишком мягко)

**Файл:** `config/slam/slam_toolbox_params.yaml`, строка 74

**Суть:**
Этот параметр — минимальный score, при котором SLAM принимает scan match как валидный.
Типичные рабочие значения: `0.45–0.55`. Значение `0.1` означает, что SLAM принимает
**практически любое совпадение**, включая ложные. В узком пространстве с 180° сканом это
создаёт риск зафиксировать неверную позу в pose graph.

**Путь решения:**
```yaml
# Было:
link_match_minimum_response_fine: 0.1
# Поднять до:
link_match_minimum_response_fine: 0.45
```

**Риск повышения:** SLAM будет реже добавлять ноды в граф — карта будет строиться медленнее
в слабо-различимых окружениях. Если среда разнообразна — проблем нет.

**Диагностика перед правкой:**
```bash
# Включить debug в slam_toolbox и смотреть на score при развороте:
debug_logging: true
# В логах будет: "Response: X" — если видишь значения 0.1–0.2 во время разворота,
# это подтверждает ложные матчи
```

## Проблема 4 — `angular_scale: 2.0` в cmd_vel fallback

**Файл:** `src/verter_admin/control/domain/odometry_policy.py`, строка 26

**Суть:**
```python
angular_scale: float = 2.0
```
При fallback на cmd_vel (если энкодеры не приходят >1 сек) угловая скорость умножается на 2.
Если это происходит даже кратковременно во время разворота — одометрия получает yaw-скачок ×2.

**Когда срабатывает:**
- Перегрузка micro-ROS агента
- Кратковременный обрыв USB
- `encoder_timeout: 1.0` истёк

**Диагностика:**
```bash
# Смотреть source в /odom:
ros2 topic echo /odom
# Или добавить лог в odometry_node — при переключении на CMD_VEL источник меняется
```

**Путь решения:**
```python
# Вариант A — убрать масштабирование в fallback:
angular_scale: float = 1.0

# Вариант B — отключить cmd_vel fallback полностью
# (если encoder_timeout истёк = проблема связи, не нужно "угадывать" позицию)
encoder_timeout: 0.5  # сократить таймаут, чтобы быстрее выявлять обрыв
```

## Проблема 5 — URDF wheel_base ≠ calibrated wheel_base (косметическое)

**Файл:** `urdf/verter_robot_minimal.urdf`

**Суть:**
- URDF: `wheel_left_joint y=0.178`, `wheel_right_joint y=-0.178` → wheel_base = **0.356m**
- Calibrated в коде: **0.374m**
- MEMORY.md: **0.362m**

Три разных значения. На навигацию не влияет (URDF joints — fixed, не используются в одометрии),
но вносит путаницу и модель в RViz неточная.

**Путь решения:**
Измерить реальное расстояние между центрами точек контакта колёс с полом.
Обновить URDF до `±(wheel_base / 2)` от измеренного значения.
Также обновить MEMORY.md — привести к единому значению.

## Проблема 6 — Слишком высокая скорость в auto-mapping для RPLidar A1

**Файлы:**
- `src/verter_admin/config/slam/slam_toolbox_params.yaml`
- `src/verter_admin/config/nav2/nav2_mapping_real_params.yaml`

**Суть:**
В `slam_toolbox_params.yaml` прямо указано, что для RPLidar A1M8 безопасный диапазон
при построении карты около `0.10-0.15 m/s`. При этом в auto-mapping был выставлен
`desired_linear_vel: 0.25` и такой же высокий лимит в `velocity_smoother`.

Это создаёт классический motion distortion:
- во время движения скан "растягивается" по времени,
- scan matcher получает геометрию, которая уже не соответствует одной позе,
- длинные стены начинают двоиться и расходиться параллельно.

**Где видно:**
- `slam_toolbox_params.yaml` содержит комментарий с рекомендацией по скорости
- `nav2_mapping_real_params.yaml` задаёт `desired_linear_vel` и `max_velocity`

**Диагностика:**
```bash
# Сравнить тот же коридор на 0.25 m/s и 0.15 m/s
# Если двойные стены резко уменьшаются — причина подтверждается
```

## Проблема 7 — Nav2 сам провоцирует развороты в тесных местах

**Файл:** `src/verter_admin/config/nav2/nav2_navigation_params.yaml`

**Суть:**
Даже если SLAM и odom были бы идеальными, текущая логика Nav2 в тесных местах сама
может загонять робота в вращение на месте:
- `use_rotate_to_heading: true`
- `allow_reversing: false`
- сравнительно большой `lookahead_dist`
- recovery behavior содержит `spin`

Механизм такой:
- робот входит в узкий проход,
- local planner считает, что курс надо быстро довыставить,
- вместо мягкой дуги или отъезда назад происходит поворот на месте,
- на скользком покрытии колёса начинают проскальзывать,
- дальше odom и scan matching расходятся ещё сильнее.

**Диагностика:**
```bash
# В RViz смотреть local costmap и траекторию контроллера
# Если перед потерей локализации робот регулярно уходит именно в spin/recovery,
# то проблема не только в SLAM, но и в поведенческой логике Nav2
```

## Проблема 8 — Слишком агрессивные угловые ограничения в behavior/controller

**Файлы:**
- `src/verter_admin/config/nav2/nav2_navigation_params.yaml`
- `src/verter_admin/config/nav2/nav2_mapping_real_params.yaml`

**Суть:**
Высокие значения `max_rotational_vel`, `rotational_acc_lim`, `max_angular_accel`
усиливают проскальзывание и делают поведение робота нервным именно там, где нужно
наоборот медленное и предсказуемое движение.

Если робот в recovery быстро раскручивается, ошибка yaw начинает расти по цепочке:
`wheel slip -> плохой odom -> плохой map->odom -> лидар не совпадает с картой`.

**Диагностика:**
```bash
# Снять bag или видео разворота в узком месте
# Если ошибка появляется сразу после резкого вращения, а не после прямого движения,
# то угловая динамика слишком агрессивна
```

## Проблема 9 — AMCL стартует с фиксированной позой `(0, 0, 0)`

**Файл:** `src/verter_admin/config/nav2/nav2_navigation_params.yaml`

**Суть:**
В конфиге AMCL включён `set_initial_pose: true` и задана фиксированная начальная поза.
Если робот физически стартует не из этой точки, локализация с самого начала получает
ложную гипотезу. В симметричных коридорах или узких местах AMCL после этого может
долго не сходиться или зацепиться за неправильную ориентацию.

**Почему это важно:**
Даже хороший odom и нормальный lidar scan не всегда быстро выводят фильтр из ложной
начальной гипотезы, если геометрия вокруг малоинформативна.

**Диагностика:**
```bash
ros2 param get /amcl set_initial_pose
ros2 param get /amcl initial_pose.x
ros2 param get /amcl initial_pose.y
ros2 param get /amcl initial_pose.yaw
```

## Проблема 10 — Odom covariance слишком оптимистична и не зависит от режима движения

**Файл:** `src/verter_admin/control/adapters/ros/odometry_node.py`

**Суть:**
Одометрия публикует фиксированные covariance и не увеличивает их при вращении на месте,
пробуксовке или fallback-режиме. В результате EKF продолжает слишком доверять odom даже
тогда, когда качество оценки движения уже резко ухудшилось.

**Почему это плохо:**
Фильтр не понимает, что источник стал менее надёжным, и продолжает тянуть `odom` за
ошибочным yaw/дистанцией.

**Диагностика:**
```bash
ros2 topic echo /odom --once
# Проверить covariance на прямом ходе и во время разворота — сейчас они не различаются
```

## Проблема 11 — IMU и odom живут в разных временных базах

**Файлы:**
- `firmware/esp32_sensors/esp32_imu_microros/esp32_imu_microros.ino`
- `src/verter_admin/control/adapters/ros/odometry_node.py`

**Суть:**
IMU публикует stamp из `millis()` ESP32, а odometry node ставит время по хостовой
системе. Если между этими источниками есть заметный сдвиг или дрожание, EKF получает
несинхронные измерения. На быстрых поворотах это особенно вредно: gyro и wheel odom
описывают разные моменты времени.

**Следствие:**
Даже корректный по знаку `vyaw` из IMU может не успевать стабилизировать yaw odom.

**Диагностика:**
```bash
ros2 topic echo /imu/data --once
ros2 topic echo /odom --once
# Сравнить header.stamp и поведение во время быстрого разворота
```

## Проблема 12 — IMU не даёт абсолютную ориентацию, только angular velocity

**Файл:** `firmware/esp32_sensors/esp32_imu_microros/esp32_imu_microros.ino`

**Суть:**
IMU публикует только гироскопический `angular_velocity.z`, а ориентация как источник
для фильтра фактически отсутствует. Это значит, что в системе нет независимого
абсолютного yaw-источника: остаются только колёса и scan matching.

В узких коридорах этого часто недостаточно.

**Диагностика:**
```bash
ros2 topic echo /imu/data --once
# Проверить orientation_covariance: если там -1, абсолютная ориентация не используется
```

## Проблема 13 — Ультразвук заявлен в costmap, но тракт топиков не сходится

**Файлы:**
- `src/verter_admin/config/nav2/nav2_navigation_params.yaml`
- `src/verter_admin/config/nav2/nav2_mapping_real_params.yaml`
- `src/verter_admin/control/adapters/ros/range_converter_node.py`
- `src/verter_admin/control/adapters/ros/proximity_safety_node.py`

**Суть:**
Конфиги costmap и safety-node ждут `LaserScan` на `/ultrasonic/ranges`, но по коду
сенсоры публикуются другой цепочкой (`Float32MultiArray` и затем набор `Range`).
Из-за этого в узких местах робот, вероятно, не получает тот ближний обзор, на который
рассчитывает конфигурация.

Это не корень проблем SLAM, но усиливает ошибки поведения в тесных проходах.

**Диагностика:**
```bash
ros2 topic list | grep ultrasonic
ros2 topic info /ultrasonic/ranges
```

## Что из уже описанного в документе подтверждается дополнительно

Подтверждаются как минимум эти пункты:
- проблема с front-only lidar действительно остаётся одним из главных факторов деградации в узких местах;
- `angular_scale: 2.0` в fallback odom остаётся сильным кандидатом на скачки yaw;
- рассогласование `wheel_base` не только косметическое для понимания модели, но и симптом того, что в проекте нет одного согласованного источника правды по кинематике.

## Что я бы считал корневыми причинами в первую очередь

1. Несогласованная кинематика базы: `wheel_base`, scale расстояния, поведение при slip.
2. Неправильная или слишком бедная геометрия лидара: front-only фильтр, возможная ошибка ориентации `lidar_link`.
3. Слишком высокая скорость и угловая динамика при картографировании и recovery.
4. Слишком сильное доверие к wheel odom в EKF при слабом независимом yaw-источнике.
5. Слабая наблюдаемость в узких местах плюс агрессивная логика Nav2.
